# Collected data

Live verification adds these public metadata files (no individual protected-provider
temperatures or forecast errors):

- `daily_collection/YYYY/MM/YYYY-MM-DD.jsonl`: provider/station/date save or failure status.
- `collection_runs/YYYY/MM/<kind>-<run>-<attempt>.json`: expected captures, workflow/job
  timestamps, discovery timing, and request duration/status. Local runs use a random ID.
- `verification/daily/` and `verification/market/`: latest `health.json`,
  `accuracy.json`, and `summary.md` generated by each workflow. Scores require common
  cases, comparable capture times, and at least five distinct target dates.

New daily rows record request start and response arrival. Older daily rows do not
have a verified arrival timestamp and are excluded from timed accuracy comparisons.
Observation collection is limited to station-dates with saved live forecasts;
settlement refreshes revisit only already-known events relevant to those forecasts.
NOAA values without verified window boundaries are retained for comparison research
but are not silently treated as Kalshi settlement outcomes. See the scoring rules
in [the project README](../README.md#live-health-and-accuracy-reports).

The collection workflow writes deterministic, date-partitioned files here:

- `forecasts/YYYY/MM/YYYY-MM-DD.jsonl` contains normalized next-day forecasts.
- `forecasts/YYYY/MM/YYYY-MM-DD.jsonl.<provider>.enc` contains encrypted next-day
  forecasts with the same normalized schema, separately for enabled `meteosource`, `openweathermap`,
  `pirate_weather`, and `visual_crossing`.
- `observations/YYYY/MM/YYYY-MM-DD.jsonl` contains NOAA/NCEI daily outcomes.
- `markets/YYYY/MM/YYYY-MM-DD.jsonl` contains contract rules and source metadata,
  partitioned by the market's temperature date and keyed by ticker/rules version.
- `market_forecasts/YYYY/MM/YYYY-MM-DD.jsonl` contains immutable first forecasts
  after a market opens, keyed by provider/event/opening timestamp. These use the
  shared `config/stations.csv` registry and a 24-hour local-standard-time window.
- `market_forecasts/YYYY/MM/YYYY-MM-DD.jsonl.<provider>.enc` contains
  encrypted market snapshots with the same immutability rules.
- `market_collection/YYYY/MM/YYYY-MM-DD.jsonl` records capture status, including
  missed openings and provider failures that must not be mistaken for data.
- `raw/<provider>/...` preserves source responses only when the collector runs
  with `--save-raw` and the source permits archival storage. Scheduled runs store
  only the normalized records. Migrated raw files use `.json.<provider>.enc`.
- `private/<provider>/` holds local decrypted exports and is ignored by Git.

Unencrypted JSONL files contain one JSON object per line. The `schema_version` field allows
future migrations without silently changing existing records.

Market forecasts use schema version 2 and link to the exact contract rule versions.
They preserve the actual fetch time, reporting-window start/end, and opening delay.
Only `eligible_for_opening_comparison=true` rows meet the configured timing tolerance;
other retained forecasts are marked `late`. The original daily research snapshots
are not replaced by market snapshots. Do not join O'Hare/Love Field observations to
Midway/DFW markets or treat NOAA/NCEI as The Weather Company's settlement report.
All future collection uses the Kalshi stations in the shared registry, including
Midway and DFW. Legacy O'Hare/Love Field rows remain unchanged for provenance and
must be excluded from Kalshi station comparisons. The NOAA lookback automatically
adds available Midway/DFW observations; historical forecasts cannot be recreated.

Open-Meteo data requires attribution under CC BY 4.0. NOAA/NCEI data is U.S.
government open data. Do not add another provider's raw or normalized data until
its terms explicitly permit long-term storage and the intended redistribution.
Use Open-Meteo's commercial endpoint and plan for commercial workloads.

OpenWeather data is provided under the Open Database License (ODbL). The stored
OpenWeather records in this repository form an adapted database and are shared
under the same ODbL terms. Credit: weather data provided by
[OpenWeather](https://openweather.co.uk/).

OpenWeather records generated from the free five-day endpoint contain extrema
derived from three-hour forecast points; they are not native daily extrema.
New rows aggregate `main.temp` and use the method
`max_min_of_3_hour_temperature`. Older `max_min_of_3_hour_points` records used
spatial min/max values and must be distinguished in analysis.
NWS and Tomorrow.io extrema are derived from hourly temperatures. All sampled
providers now reject incomplete local-day coverage and store sample counts;
daylight saving transitions are handled as 23-hour or 25-hour days.
Weatherbit and Tomorrow.io output is written only when the corresponding
archival-authorization repository variable is enabled.

## Pirate Weather and Visual Crossing

Both providers use hourly temperature samples, with full 23/24/25-hour local-day
coverage for morning snapshots and full 24-hour standard-time coverage for market
snapshots. Pirate Weather's daytime `temperatureHigh` and overnight
`temperatureLow` are not used as full-day extrema. Visual Crossing requests only
the civil dates needed by the window and `include=hours,fcst`; every included
hour must have `source=fcst`. Neither adapter requests historical data. Retrieved
times are collection times, not claims about model initialization times.

Attribution is included in every normalized record:
- [Pirate Weather](https://pirateweather.net/) ([API documentation](https://docs.pirateweather.net/en/latest/API/))
- [Visual Crossing](https://www.visualcrossing.com/) ([Timeline documentation](https://www.visualcrossing.com/resources/documentation/weather-api/timeline-weather-api/))

[Visual Crossing's storage guidance](https://www.visualcrossing.com/resources/documentation/can-i-cache-and-store-visual-crossing-weather-data/)
distinguishes application archives from public downloads. Encryption controls
access. Each provider’s terms determine permitted uses. Pirate Weather uses public
weather models with upstream data terms. Preserve attribution when sharing results.

## Archive key setup and migration

Run these commands from the repository root. New protected files use authenticated
Fernet encryption (`FAD2`) with a dedicated `DATA_ENCRYPTION_KEY`. For an existing
archive, use its current key. For a new installation, generate a key once:

```shell
python src/create_archive_key.py
```

The command creates an owner-only, gitignored `.env` containing a random 32-byte
key encoded as URL-safe base64. It refuses to overwrite an existing file. Back
up the key securely and copy its value to the Actions repository **secret**
`DATA_ENCRYPTION_KEY`. Local commands read this file when passed `--key-file .env`.

### Migrate older files

```shell
# Preview changes, then apply the verified migration.
python src/migrate_archives.py --key-file .env
python src/migrate_archives.py --key-file .env --apply
```

Legacy `FAD1` Visual Crossing files require the original `VISUALCROSSING_API_KEY`
in the environment. To migrate a subset, add `--providers` followed by provider
IDs, for example `--providers openweathermap pirate_weather`. The migration
encrypts permitted forecast rows and raw responses, preserving original capture
times. It verifies inputs and encrypted outputs before removing plaintext copies.
If interrupted, rerun the command to finish. Weatherbit and Tomorrow.io records
are excluded. Earlier Git revisions, forks and clones can still contain plaintext.

Collection workflows run migration after capture. The dedicated
[migration workflow](../.github/workflows/migrate-archives.yml) can also run
manually or when changes to its workflow or migration code reach `main`.
It migrates saved files and rebuilds reports without calling weather APIs.

### Rotate the key

Coordinate rotation with collection jobs so that writers and readers switch keys
together. Keep a secure copy of the current key, generate a new key in a separate
private file, then run:

```shell
python src/migrate_archives.py --key-file NEW_PRIVATE_FILE --previous-key-file OLD_PRIVATE_FILE --apply
```

Update the Actions secret to match the migrated archives. Keep old keys for Git
revisions and backups that still use them.

### Export private forecasts

```shell
python src/export_private_forecasts.py --key-file .env
```

The exporter writes decrypted JSONL to the gitignored `data/private/<provider>/`
directory, preserving the daily and market datasets. Keep those files private.
For ordinary scoring, the reporting command decrypts forecasts in memory.
